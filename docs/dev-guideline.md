# 開発指針（全 project 共通）

目的：過去のコードをテンプレとして最大限流用し、全 project で高品質かつ高速に開発する。その効果を数字で測り、改善する。

## 進め方

1. 要件：受入条件と一緒に決める
2. サービス分割：まずはサービスとして切り出す
3. 再設計：分割結果を見直し、サービスを足す・減らす。小さすぎるサービスは統合する（全部を統合することもある）
4. 最低限の IF 設計
5. テンプレ選択：これまでに作ったコードから、今回の設計に一番合うものを探す
6. 必要な部分の移植、または依存として取り込む。どちらにするかは設計の一部としてその場で決め、両者のバランスを最大限とる
7. 改修
8. テンプレがない部分は新しく追加する

## 完了条件とテスト

最後にまとめて作らない。設計の各工程で、その工程が決めた境界の単位で決める。

| タイミング | 決めるもの | 方法 |
|---|---|---|
| 要件 | 受入条件（ユーザーから見た完了） | 具体的な値の入出力例で書く。曖昧な語（「適切に」「高速に」）は使わない。異常系を 1 つ以上入れる |
| サービス分割・再設計 | サービスごとの責務の完了条件 | 返すもの・返さないものを書く。統合・分離したら書き直す |
| IF 設計 | 契約テスト（Input → Output の例） | 境界ごとに正常系・境界値・異常系の例を表で書く。これがテストケースになる |
| テンプレ選択・移植 | 移植したコードの現状の振る舞い | テストがあるテンプレを優先し、テストも一緒に移植する。なければ改修前に現状の振る舞いを固定するテスト（特性テスト）を書く |
| 実装 | 単体テスト | 小さい単位で先に書く |

- done は実行できるコマンドで書く。人の判断を挟まない
- テストを書く人と実装する人を分ける。または、テストを別のエージェントがレビューする

## 計測

仮説：速度 × 品質 は、テンプレ適合率に比例する。テンプレの量は適合率を上げるための入力。要件が特殊だと適合率が下がる。

| 項目 | 定義 |
|---|---|
| テンプレ適合率 | テンプレで賄えた境界数 ÷ 設計上の全境界数。境界ごとに「流用 / 一部流用 / 新規」を設計時に記録する |
| 修正量 | 流用した境界ごとの、テンプレからの差分行数 |
| 速度 | 着手からリリースまでの時間。リリースに含まれた境界数も一緒に記録する（比較するときに使う） |
| 品質 | 手戻り回数、レビュー指摘数、リリース後の不具合数 |

## テンプレ Index

実装はアプリ [searchcode](../searchcode/README.md) として切り出す。

- project ごとに上の数字を記録する。数が溜まったら、仮説どおりかを実データで確かめる
- 適合率が低かった境界は、新しいテンプレとして Index に登録する
- Index には IF の形と、テストの有無・カバー範囲を載せる。テンプレ選択と契約テストの流用に使う
