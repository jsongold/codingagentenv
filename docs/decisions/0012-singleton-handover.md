# ADR-0012: 状態を持つ singleton の新しい版への引き継ぎ

- 日付：2026-09-28
- 状態：採用

## 文脈
cad は 1 台の VM で 1 つだけ動く常駐プロセス（singleton）で、main に merge されるたびに新しい版へ入れ替わる（pull 型、Docker Swarm 1 台、ADR-0011 / PR #45）。Web サーバーのように複数並べて順に替えることはできず、「状態を持つ singleton をどう引き継ぐか」という古くからある問題になる。将来 orchd が常駐して task を振り分けるようになると、二重に振り分けないことも必要になる。

2026 年時点の手法を調べた（opencode 調査、#40 のコメント）。主流は「自作しない」: コードと状態を一緒に進化させるなら版を固定できる durable execution（Temporal Worker Versioning、Restate の版を固定したデプロイ）、コンテナ 1 つの singleton なら Lease による leader election + fencing token + graceful drain。

## 決定
**引き継ぎの方式は、プロセスの性質で決める。次の 4 つを問い、答えに合う最小の方式を選ぶ。**
1. 新旧が同時に動いて害があるか（二重に処理してよいか）
2. 状態をどう渡すか（取り直せるか、保存が要るか、外部に置くか）
3. 途中の仕事をどうするか（捨ててよいか、最後まで終わらせるか）
4. 切り替え中の利用者をどうするか（やり直させる、待たせる）

**cad（A: 読むだけ、二重に動いても害が無い、状態は取り直せる）→ 最小限**
- 止めてから起動する（stop-first、Swarm のヘルスチェックに失敗したら自動で元に戻す）
- 最後の usage をファイルに保存し、起動時に「古い」の印付きで読み込む（24 時間以内）
- `/healthz?ready` は、保存した値を読み込むか初回の収集が終わるまで 503
- orchd は、準備中なら defer、つながらなければ 2 秒 × 3 回やり直す
- 新しい版は古い設定ファイルも読めること。読めない変更は、起動時の変換を入れる

**常駐して task を振り分けるもの（B: 二重に振り分けてはいけない）→ 自作しない**
- durable execution のエンジン（Hatchet / Temporal / Restate。#40 で選ぶ）に載せ、途中の振り分けは旧版で最後まで処理し、新しい仕事だけ新版に回す
- 振り分けのたびに冪等性キー（task ID）を付ける
- 「どの Orchestrator が今振り分けてよいか」を持つなら、Lease + fencing token で守る

## 検討して却下した案
| 案 | 却下理由 |
|---|---|
| cad に leader election / Lease を入れる | 二重に動いても害が無いので不要。ポートの競合は stop-first で避けられる |
| cad をプロセスごと保存・復元（CRIU） | 扱いにくく、状態は取り直せば済む |
| 待ち受けソケットの引き継ぎ（systemd FD store 等）で停止 0 秒にする | 数秒の停止は許容できる。コンテナとの組み合わせが複雑。必要になったら再検討 |
| 常駐の Orchestrator を「スケジューラ daemon + 自前のキュー」で作る | 二重の振り分けや split-brain の典型的な原因（ADR-0001 / 0002 の教訓とも一致） |

## 影響
- 良い影響：cad は追加の仕組み無しで入れ替えられ、切り替え直後も窓の判定が効く。B の判断基準が先に決まる
- 受け入れたトレードオフ：cad の入れ替えでは数秒止まる。保存した usage は最大 24 時間古い可能性がある（「古い」の印で区別する）
- 再検討する条件：停止 0 秒が必要になったとき。cad が書き込みを伴う処理を持ったとき（fencing が要る）。orchd が常駐したとき（B を実装する）
