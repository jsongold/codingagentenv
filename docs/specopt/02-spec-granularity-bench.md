# SpecOpt：Spec の粒度とトークン消費の実測

目的：CA に渡す Spec の粒度と書き方で、トークン消費と合否がどう変わるかを、品質の高い OSS の実コミット 29 件で測り、現時点の最適な Spec を決める材料を残す。

- 実施日：2026-10-12〜13。親：Epic CAO-2、Story CAO-4。前提の調査は `01-web-research.md`
- 進め方：test → research（Web 再調査）→ Spec を変えて再 test、を 3 回
- 状態：1 回目と 2 回目は完了。3 回目は実行中（4 章に追記する）

## 要約

- Spec を細かくすると総トークンが減る。目的だけ（x1）に対して、ファイルと決定済みの変更まで書く（x5）と 0.86 倍、関数単位の場所と手順まで書く（x10）と 0.69 倍。
- 合格率は全条件で 100%。テストを最初から渡す条件では、Spec の粒度は品質ではなくコストにだけ効いた。
- 場所をファイル単位から関数単位に細かくしても、変わらない（1.00 倍）。
- 「テストは 1 回、通ったら止まる、1 行で返す」という進め方の指示は、指示どおりに動くが、総トークンはほとんど減らない（x5 で 0.93 倍、x10 で 1.00 倍）。CA が編集を 1 か所ずつ Edit ツールで行うようになり、減らしたターンを打ち消すため。
- 総トークンはターン数にほぼ比例する（1 ターン約 1.1 万トークン）。残っている最大の削りしろは、編集のターン数と、毎ターン読み直される固定分。

## 2. 1 回目：粒度 x1 / x5 / x10

| 粒度 | 中身 | 語数（中央値、受入の節を含む） |
|---|---|---|
| x1 | 目的だけ（1〜2 文） | 95 |
| x5 | 目的、触るファイル、決定済みの変更、制約 | 244 |
| x10 | x5 に加えて、関数単位の場所、順番つきの手順、従う既存パターン | 437 |

結果（29 件 × 3 粒度 × 2 回 = 174 回。全部合格、権限の拒否とエラーは 0 件）

| 粒度 | 総トークン（中央値） | 出力トークン（中央値） | ターン数（中央値） | 時間（中央値） |

| x10 | 60,233 | 1,449 | 5.0 | 17.4 秒 |

| x5 ÷ x1 | 0.86 [0.69, 0.98] | 0.86 [0.76, 0.95] | 69.0% |

| x10 ÷ x5 | 0.82 [0.77, 1.03] | 0.90 [0.80, 1.01] | 62.1% |

| 区分 | 件数 | x5 | x10 |
|---|---|---|---|
| Go | 16 | 0.83 | 0.71 |
| Python | 9 | 0.92 | 0.75 |
| TypeScript | 4 | 0.62 | 0.54 |
| S（12 行以下） | 10 | 0.76 | 0.70 |
| M（13〜45 行） | 10 | 0.89 | 0.79 |
| L（46 行以上） | 9 | 0.90 | 0.55 |

実行ごとのばらつき（同じ条件 2 回の、総トークンの最大 ÷ 最小）

| 粒度 | 中央値 | 最大 |
|---|---|---|
| x1 | 1.28 | 3.02 |
| x5 | 1.14 | 2.47 |
| x10 | 1.06 | 1.83 |

言えること
- x5 も x10 も、x1 より総トークンが少ない（信頼区間が 1 をまたがない）。
- x5 から x10 への上積みは 0.82 倍の傾向だが、信頼区間が 1 をまたぐ。
- 大きい変更では x10 がよく効き（0.55 倍）、小さい変更では x5 と x10 の差が小さい（0.76 と 0.70）。
- Spec が細かいほど、実行ごとのばらつきが小さい。

## 3. 2 回目：場所の細かさと「進め方」

1 回目で、粒度に関係なく「テストを複数回実行する」「終わりに 600〜700 字の報告を書く」が残っていた。再調査で、OSS のハーネスが「まとめて呼ぶ」「探索を早く切り上げる」を指示していることを確かめたので、次の 3 つを試した。

| 変種 | 中身 |
|---|---|
| x5f | x5 の「触るファイル」を、関数単位の場所に置き換える |
| x5fw | x5f に「進め方」の 4 行を足す |
| x10w | x10 に同じ 4 行を足す |

「進め方」の 4 行：必要なものだけ読み、独立した読み取りと検索は 1 回にまとめる / 編集を全部終えてから受入コマンドを 1 回だけ実行する / 通ったら止まる / 最後は 1 行だけ返す。

結果（29 件 × 3 変種 × 2 回 = 174 回。全部合格、権限の拒否とエラーは 0 件）

| 比 | 総トークン | ターン数 |
|---|---|---|
| x5f ÷ x5 | 1.00 [0.91, 1.00] | 1.00 [0.92, 1.08] |
| x5fw ÷ x5 | 0.93 [0.83, 1.00] | 1.00 [0.93, 1.15] |
| x10w ÷ x10 | 1.00 [0.96, 1.02] | 1.00 [1.00, 1.05] |

x1 を基準にすると、x5f が 0.83、x5fw が 0.73、x10 が 0.69、x10w が 0.67。

言えること
- 場所を関数単位にしても変わらない。x5 の「決定済みの変更」が、すでに関数名を含んでいることが多いためと考えられる（未検証）。
- 「進め方」は、x5 で約 7% 減る傾向（信頼区間の上端が 1.00）。x10 には上積みがない。
- ターン数はどちらも減っていない。理由は 5 章。

## 5. 何にターンを使っているか

transcript からツールの呼び出しを数えた。x1 / x5 / x10 は各 58 回、変種は各 29 回（1 回分の時点）。

| 項目 | x1 | x5 | x10 | x5f | x5fw | x10w |
|---|---|---|---|---|---|---|
| 最初の編集までのツール呼び出し（中央値） | 3 | 2 | 1 | 2 | 2.5 | 1 |
| テストの実行回数（平均） | 1.98 | 1.48 | 1.45 | 1.52 | 1.07 | 1.07 |
| テスト以外の Bash（平均） | 1.72 | 1.03 | 0.40 | 0.52 | 0.28 | 0.07 |
| Edit ツールの回数（平均） | 0.52 | 1.45 | 1.90 | 1.55 | 3.03 | 2.69 |
| ツール結果の文字数（中央値） | 9,848 | 6,039 | 4,059 | 6,997 | 4,958 | 3,726 |
| 終わりの報告の長さ（中央値） | 613 字 | 700 字 | 668 字 | 709 字 | 26 字 | 26 字 |

- 総トークン ÷ ターン数の中央値は 10,885、総トークンとターン数の相関係数は 0.75（261 回）。毎ターン読み直される固定分（システムプロンプトとツール定義）が支配している。
- 粒度を上げると減るのは、編集に入るまでの探索、テスト以外の Bash、ツール結果の量。
- 指示が無いとき、CA は Bash のスクリプト 1 本で全部の編集を済ませることが多い。Edit ツールを 1 度も使わない実行は、x1 で 58 回中 36 回、x5 で 23 回、x10 で 14 回。
- 「進め方」を足すと、テストはほぼ 1 回になり、終わりの報告は 26 字になる。その一方で Edit ツールの回数がほぼ倍になる（1.55 → 3.03、1.90 → 2.69）。1 か所ずつ編集するターンが増え、減らしたターンを打ち消している。

### 実測があるもの

### 見つからなかったもの

- Spec の語数を変えて、コーディング agent のトークンとターンを比べた公開の実測
- 「編集を 1 回にまとめる」指示と「1 か所ずつ編集」を、同じモデル・同じタスクで比べた公開の実測
- 「テストは 1 回」「終わりの報告を短く」の指示だけを変えた公開の実測
- 並列のツール呼び出しの実測は、Web 調査のタスクのもの（[arXiv 2602.07359](https://arxiv.org/abs/2602.07359)）で、コーディングではない

### opencode の出力から直した点

- 「編集箇所を与えるとコストが $2.18 → $1.21」は、情報を積み上げた累積の値。編集箇所だけの場合は $0.84
- 「要件を全部書くと性能が下がる」「200 語を超えると性能が下がる」は、コーディング agent ではなく文章生成や関数単位のコード生成の結果で、後者は 2 つのベンチの片方だけ
- 「apply_patch は 1 回で複数ファイルを変更できる」は誤り。API の原文は「1 回の呼び出しは 1 ファイルの操作」

## 7. 途中で直したこと

- 最初の 90 回は、68 回で CA のコマンドが権限で拒否されていた（Python スクリプトでの書き換え、相対パスやパイプつきのテスト実行）。拒否はやり直しのターンを生み、細かい Spec ほど不利に出るので、この分は数字に使っていない。
- Bash サンドボックスを有効にし、その中の Bash を全部許可して取り直した。以後の実行では拒否は 0 件。
- サンドボックスを有効にすると、1 ターンあたりの固定分が約 7.7K から約 11K トークンに増える。全条件に同じだけ乗る。
- 取り直しの途中で、9 回が利用枠の上限（429）でエラー終了した。この 9 行は除いて取り直した。

## 8. 限界

- テストを最初から渡しているので、全条件が 100% 合格した。Spec の粒度が品質に効く場面（テストが無い、要件があいまい）は測れていない。
- Spec は実コミットの差分から作った。実運用で同じ細かさの Spec を、実装より安く作れるかは測っていない（CAO-82 の範囲）。
- モデルは sonnet の 1 つ、CA は Claude Code の 1 つ。ほかのモデルや CA に当てはまるかは不明。
- ケースは 29 件、変更は最大 133 行。大きい機能追加や、複数モジュールにまたがる変更は含まない。
- OSS の有名 repo なので、モデルが学習時に実コミットを見ている可能性がある。2026 年のコミットを優先したが、排除はできていない。
- 総トークンは 4 内訳（input / output / cache read / cache creation）の単純和。請求額やサブスクの利用枠とは重みが違う。

実行スクリプトと生の結果は一時ディレクトリにあり、repo には入れていない。
