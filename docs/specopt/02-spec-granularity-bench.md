# SpecOpt：Spec の粒度とトークン消費の実測

目的：CA に渡す Spec の粒度と書き方で、トークン消費と合否がどう変わるかを、品質の高い OSS の実コミット 29 件で測り、現時点の最適な Spec を決める材料を残す。

- 実施日：2026-10-12〜13。親：Epic CAO-2、Story CAO-4。前提の調査は `01-web-research.md`
- 進め方：test → research（Web 再調査）→ Spec を変えて再 test、を 3 回
- 状態：3 回とも完了。10 条件 × 29 件 × 2 回 = 580 回を実行し、全部合格。権限の拒否、エラー終了、テストの改変は 0 件

## 要約

- Spec を細かくすると総トークンが減る。目的だけ（x1）に対して、ファイルと決定済みの変更まで書く（x5）と 0.86 倍、関数単位の場所と手順まで書く（x10）と 0.69 倍。
- 合格率は全条件で 100%。テストを最初から渡す条件では、Spec の粒度は品質ではなくコストにだけ効いた。
- 場所をファイル単位から関数単位に細かくしても、変わらない（1.00 倍）。
- 「テストは 1 回、通ったら止まる、1 行で返す」という進め方の指示は、指示どおりに動くが、総トークンはほとんど減らない（x5 で 0.93 倍、x10 で 1.00 倍）。CA が編集を 1 か所ずつ Edit ツールで行うようになり、減らしたターンを打ち消すため。
- 「編集と受入コマンドの実行を 1 回にまとめる」と指示すると、ターン数が 0.69〜0.78 倍、出力トークンが 0.60 倍、時間が 0.69〜0.78 倍になる。総トークンは 0.89 倍（x5 では信頼区間が 1 をまたがない）。
- CA に渡すツールを Bash だけにすると、同じ Spec でさらに 0.79 倍になる。これは Spec ではなくハーネスの設定の効果。
- 最も少なかった条件（x10 + まとめる指示 + Bash だけ）は、x1 の 0.53 倍で、29 件すべてで x1 より少なかった。

### 現時点の最適な Spec

実測から言える範囲での答え。

| 要素 | 判断 | 根拠 |
|---|---|---|
| 目的、触るファイル、決定済みの変更、制約、受入コマンド（x5 相当） | 書く | x1 の 0.86 倍。現行の Task 仕様（`skills/cco/task-spec.md`）とほぼ同じ形 |
| 関数単位の場所、順番つきの手順、従う既存パターン（x10 相当） | 大きい変更のときだけ書く | 46 行以上の変更で x1 の 0.55 倍。小さい変更では x5 との差が小さい |
| 場所だけを関数単位にする | 要らない | x5 と変わらない（1.00 倍） |
| 「読み取りは 1 回、編集と受入コマンドの実行を 1 回にまとめる、通ったら止まる、1 行で返す」の 4 行 | 足す | x5 に足して総トークン 0.89 倍、時間 0.69 倍、出力 0.60 倍。合格率は変わらない |
| 「必要なものだけ読む、テストは 1 回、通ったら止まる、1 行で返す」の 4 行（編集のまとめ方を言わない版） | 足さない | 総トークンがほとんど減らない |

条件つきの答えであることに注意する。テストを最初から渡した場合の結果で、Spec を書くコストは含まない（8 章）。

## 3. 2 回目：場所の細かさと「進め方」

1 回目で、粒度に関係なく「テストを複数回実行する」「終わりに 600〜700 字の報告を書く」が残っていた。再調査で、OSS のハーネスが「まとめて呼ぶ」「探索を早く切り上げる」を指示していることを確かめたので、次の 3 つを試した。

| 変種 | 中身 |
|---|---|
| x5f | x5 の「触るファイル」を、関数単位の場所に置き換える |
| x5fw | x5f に「進め方」の 4 行を足す |
| x10w | x10 に同じ 4 行を足す |

「進め方」の 4 行：必要なものだけ読み、独立した読み取りと検索は 1 回にまとめる / 編集を全部終えてから受入コマンドを 1 回だけ実行する / 通ったら止まる / 最後は 1 行だけ返す。

結果（29 件 × 3 変種 × 2 回 = 174 回。全部合格、権限の拒否とエラーは 0 件）

| 比 | 総トークン | ターン数 |
|---|---|---|
| x5f ÷ x5 | 1.00 [0.91, 1.00] | 1.00 [0.92, 1.08] |
| x5fw ÷ x5 | 0.93 [0.83, 1.00] | 1.00 [0.93, 1.15] |
| x10w ÷ x10 | 1.00 [0.96, 1.02] | 1.00 [1.00, 1.05] |

x1 を基準にすると、x5f が 0.83、x5fw が 0.73、x10 が 0.69、x10w が 0.67。

言えること
- 場所を関数単位にしても変わらない。x5 の「決定済みの変更」が、すでに関数名を含んでいることが多いためと考えられる（未検証）。
- 「進め方」は、x5 で約 7% 減る傾向（信頼区間の上端が 1.00）。x10 には上積みがない。
- ターン数はどちらも減っていない。理由は 5 章。

## 4. 3 回目：編集をまとめる指示

2 回目で、進め方の指示が Edit ツールの回数を増やしてターンを打ち消していた（5 章）。2 度目の再調査で「編集を 1 回にまとめる指示」を測った公開の実測は見つからなかったので、自分で測った。

| 変種 | 中身 |
|---|---|
| x1o / x5o / x10o | 各粒度に「まとめる指示」の 4 行を足す |
| x10ob | x10o と同じ文面で、CA に渡すツールを Bash だけにする（既定は Bash / Edit / Read / Write / Glob / Grep） |

「まとめる指示」の 4 行：対象のコードは 1 回で読む / 編集と受入コマンドの実行を、できれば同じ 1 回にまとめる（例：ファイルを書き換えてからコマンドを実行する 1 本のシェルコマンド）/ 通ったらすぐ止まる / 最後は 1 行だけ返す。

言えること
- まとめる指示は、ターン数・出力・時間を確実に減らす。総トークンの減りは約 11% で、x5 では信頼区間が 1 をまたがず、x10 ではまたぐ。
- 目的だけの Spec（x1）にまとめる指示を足しても、総トークンは減らない（0.98 倍）。何を変えるかが決まっていないと、まとめられない。
- ターン数ほどには総トークンが減らない。1 回の実行につき約 1.1 万トークンのキャッシュ作成が、ターン数に関係なくかかっている（中央値は x10 で 10,947、x10o で 10,644）。

## 5. 何にターンを使っているか

transcript からツールの呼び出しを数えた。各条件 58 回。

| 項目 | x1 | x5 | x10 | x5fw | x10w | x5o | x10o | x10ob |
|---|---|---|---|---|---|---|---|---|
| テストの実行回数（平均） | 1.98 | 1.48 | 1.45 | 1.10 | 1.07 | 1.55 | 1.38 | 1.48 |
| テスト以外の Bash（平均） | 1.72 | 1.03 | 0.40 | 0.26 | 0.10 | 1.69 | 1.57 | 1.60 |
| Read ツールの回数（平均） | 0.90 | 1.16 | 0.86 | 1.34 | 1.02 | 0.19 | 0.10 | 0 |
| Edit ツールの回数（平均） | 0.52 | 1.45 | 1.90 | 2.83 | 2.79 | 0.19 | 0.33 | 0 |
| Edit を 1 度も使わない実行（58 回中） | 36 | 23 | 14 | 6 | 6 | 52 | 48 | 58 |
| ツール結果の文字数（中央値） | 9,848 | 6,039 | 4,059 | 5,234 | 3,723 | 6,475 | 4,526 | 4,291 |
| 終わりの報告の長さ（中央値） | 613 字 | 700 字 | 668 字 | 26 字 | 26 字 | 26 字 | 26 字 | 26 字 |

最初の編集までのツール呼び出し（中央値）は、x1 が 3、x5 が 2、x10 が 1。

- 総トークン ÷ ターン数の中央値は 11,970、総トークンとターン数の相関係数は 0.77（580 回）。毎ターン読み直される固定分（システムプロンプトとツール定義）が大きい。
- 粒度を上げると減るのは、編集に入るまでの探索、テスト以外の Bash、ツール結果の量。
- 指示が無いとき、CA は Bash のスクリプト 1 本で全部の編集を済ませることが多い。Edit ツールを 1 度も使わない実行は、x1 で 58 回中 36 回ある。
- 「進め方」（x5fw / x10w）を足すと、テストはほぼ 1 回になり、終わりの報告は 26 字になる。その一方で Edit ツールの回数がほぼ倍になる（1.45 → 2.83、1.90 → 2.79）。1 か所ずつ編集するターンが増え、減らしたターンを打ち消している。
- 「まとめる指示」（x5o / x10o）を足すと、読み取りも編集も Bash で行うようになる。Read と Edit はほぼ使われず、Edit を使わない実行が 58 回中 48〜52 回になる。テストの実行回数は減らない（1.38〜1.55）。

### 見つからなかったもの

- Spec の語数を変えて、コーディング agent のトークンとターンを比べた公開の実測
- 「編集を 1 回にまとめる」指示と「1 か所ずつ編集」を、同じモデル・同じタスクで比べた公開の実測
- 「テストは 1 回」「終わりの報告を短く」の指示だけを変えた公開の実測
- 並列のツール呼び出しの実測は、Web 調査のタスクのもの（[arXiv 2602.07359](https://arxiv.org/abs/2602.07359)）で、コーディングではない

### opencode の出力から直した点

- 「編集箇所を与えるとコストが $2.18 → $1.21」は、情報を積み上げた累積の値。編集箇所だけの場合は $0.84
- 「要件を全部書くと性能が下がる」「200 語を超えると性能が下がる」は、コーディング agent ではなく文章生成や関数単位のコード生成の結果で、後者は 2 つのベンチの片方だけ
- 「apply_patch は 1 回で複数ファイルを変更できる」は誤り。API の原文は「1 回の呼び出しは 1 ファイルの操作」

## 7. 途中で直したこと

- 最初の 90 回は、68 回で CA のコマンドが権限で拒否されていた（Python スクリプトでの書き換え、相対パスやパイプつきのテスト実行）。拒否はやり直しのターンを生み、細かい Spec ほど不利に出るので、この分は数字に使っていない。
- Bash サンドボックスを有効にし、その中の Bash を全部許可して取り直した。以後の実行では拒否は 0 件。
- サンドボックスを有効にすると、1 ターンあたりの固定分が約 7.7K から約 11K トークンに増える。全条件に同じだけ乗る。
- 取り直しの途中で、9 回が利用枠の上限（429）でエラー終了した。この 9 行は除いて取り直した。

## 8. 限界

- テストを最初から渡しているので、全条件が 100% 合格した。Spec の粒度が品質に効く場面（テストが無い、要件があいまい）は測れていない。
- Spec は実コミットの差分から作った。実運用で同じ細かさの Spec を、実装より安く作れるかは測っていない（CAO-82 の範囲）。
- モデルは sonnet の 1 つ、CA は Claude Code の 1 つ。ほかのモデルや CA に当てはまるかは不明。
- ケースは 29 件、変更は最大 133 行。大きい機能追加や、複数モジュールにまたがる変更は含まない。
- OSS の有名 repo なので、モデルが学習時に実コミットを見ている可能性がある。2026 年のコミットを優先したが、排除はできていない。
- 総トークンは 4 内訳（input / output / cache read / cache creation）の単純和。請求額やサブスクの利用枠とは重みが違う。定価換算のコストで見ると差は小さくなる（x10o ÷ x10 は 0.90 [0.87, 0.97]、x10ob ÷ x10 は 0.89 [0.79, 0.92]）。
- 「まとめる指示」は、CA に Bash のスクリプトでファイルを書き換えさせる。今回は合格率が下がらなかったが、専用の編集インターフェースを外すと解決率が下がるという古い実測（SWE-agent、GPT-4 Turbo）もある。変更が大きい場合やテストが無い場合の安全性は測っていない。
- ツールを Bash だけにする条件は、x10 の 1 条件でしか測っていない。
